# VidMuse 前端工作台与交互流程规范

> 文档目标：给出第一版前端工作台的初步设计方案。重点不是视觉稿，而是页面结构、状态联动、交互路径、SSE 更新方式、阶段产物展示和局部修改流程。
>
> 说明：这份文档是“前端骨架设计”，不是最终 UI 稿，也不是高保真原型。后续在 API 稳定后，还需要单独产出原型图和 UI 设计稿。

---

## 1. 文档定位

当前阶段，前端设计的目标不是追求精美，而是先把这几个问题定清楚：

- 页面怎么组织
- 用户如何从输入走到成片
- 左侧 Pipeline、中间工作区、右侧 Chat 怎么联动
- SSE 到来后，前端怎么刷新状态
- 版本、确认、选项、局部返工如何操作

这份文档直接服务于：

- 前端目录结构
- 页面路由设计
- 状态管理设计
- 组件拆分
- 与后端 API/SSE 的接口方式

---

## 2. 前端设计目标

第一版前端必须做到：

- 项目创建简单直接
- 流程状态可见
- 中间产物可见
- 用户修改路径清晰
- 决策和确认不会丢
- 多轮返工可追踪
- 不依赖“聊天历史想象当前状态”

第一版前端不追求：

- 高级视频编辑器体验
- 复杂拖拽时间线
- 花哨的动效
- 大量自定义面板布局

## 3. 页面结构总览

### 3.1 路由建议

建议第一版页面路由结构：

- `/login`
- `/projects`
- `/projects/:projectId`

其中：

- `/login`：账号密码登录
- `/projects`：项目列表页
- `/projects/:projectId`：主工作台页

### 3.2 主工作台布局

主工作台采用三栏布局：

```text
┌─────────────┬──────────────────────────────┬──────────────┐
│ 左侧流程栏  │ 中间工作区                   │ 右侧对话栏   │
│ Pipeline    │ 当前阶段内容 / 画布 / 列表   │ Chat Agent   │
└─────────────┴──────────────────────────────┴──────────────┘
```

### 3.3 三栏职责

#### 左侧流程栏

负责：

- 显示项目当前阶段
- 显示各阶段状态
- 切换查看阶段内容
- 呈现哪些阶段是 stale / blocked / ready

#### 中间工作区

负责：

- 显示当前阶段产物
- 执行当前阶段的主要操作
- 查看版本
- 查看局部对象

#### 右侧对话栏

负责：

- 用户输入自然语言需求
- Agent 反问
- 展示选项卡
- 展示确认卡
- 展示执行反馈

- 复制项目
- 归档项目

### 4.3 项目工作台页

这个页面是全系统核心。

顶部建议显示：

- 项目名称

- 总体状态提示
- 导出按钮

## 5. 左侧 Pipeline 设计

### 5.1 节点列表

左侧按固定阶段显示：

- 输入
- 音频分析
- 创意方案
- 角色与风格
- 镜头计划
- 分镜 Storyboard
- 视频片段
- 时间线
- 导出

### 5.2 每个阶段节点展示内容

每个节点至少显示：

- 阶段名
- 当前状态
- 当前版本号
- 是否 stale
- 是否有待确认项
- 最近更新时间

### 5.3 节点状态设计

节点状态建议统一成：

- `未开始`
- `进行中`
- `已就绪`
- `已过期`
- `失败`
- `等待确认`

### 5.4 节点点击行为

点击节点后：

- 中间工作区切换到该阶段详情
- 右侧 Chat 保持当前对话不丢
- 顶部 breadcrumb 更新

## 6. 中间工作区设计

### 6.1 工作区本质

中间工作区不是单一页面，而是按当前阶段切换不同视图。

### 6.2 输入阶段视图

需要展示：

- 音频上传状态
- 已选时间片段
- 参考图上传区
- 初始需求文本
- 输出比例和分辨率

动作：

- 上传音频
- 拖动选择音频区间
- 上传图片
- 保存输入规格

### 6.3 音频分析阶段视图

需要展示：

- 波形
- beat 标记
- section 标记
- 歌词时间轴
- 情绪/能量曲线简图

动作：

- 重跑分析
- 修改区间
- 查看分析摘要

### 6.4 创意方案阶段视图

需要展示：

- creative brief
- style direction
- mood tags
- narrative / performance 比例

动作：

- 接受方案
- 切换方案版本
- 请求重新生成方案

### 6.5 角色与风格阶段视图

需要展示：

- 角色卡
- 风格卡
- 参考图
- 锁定状态

动作：

- 替换参考图
- 锁定角色
- 锁定风格
- 查看历史版本

### 6.6 镜头计划阶段视图

需要展示：

- shot 列表
- 每个 shot 的时长
- 对应歌词
- 情绪标签
- lipsync 标记

动作：

- 点击某个 shot 查看详情
- 重新排序
- 局部修改 shot

### 6.7 Storyboard 阶段视图

需要展示：

- 分镜卡片网格
- 每个 shot 的关键帧
- prompt 摘要

动作：

- 单帧重生成
- 替换参考图
- 局部编辑
- 批量查看

### 6.8 视频片段阶段视图

需要展示：

- 每个 shot 的 clip 缩略图
- 状态
- provider
- 成本摘要

动作：

- 重生成某个 clip
- 切换 clip 版本
- 标记为通过

### 6.9 时间线阶段视图

第一版只做轻量时间线：

- 按顺序显示 segments
- 展示字幕轨
- 展示音频波形
- 展示当前 preview

动作：

- 替换某个 segment
- 调整字幕文本
- 切换 timeline 版本
- 生成 preview

### 6.10 导出阶段视图

需要展示：

- 导出配置
- 导出历史
- 导出结果链接

动作：

- 生成预览版
- 生成高清版

## 7. 右侧 Chat 栏设计

### 7.1 右侧 Chat 的定位

它不是普通聊天窗口，而是“控制面板 + 解释面板”。

它负责：

- 输入自然语言需求
- 接收反问
- 点选结构化选项
- 确认高影响动作
- 理解当前阶段
- 快速触发局部修改

### 7.2 右侧内容类型

#### 普通文本消息

例如：

- “我先分析这段音频的节拍结构。”

#### 反问消息

例如：

- “你希望副歌更偏演唱镜头，还是偏氛围镜头？”

#### 选项卡消息

例如：

- 三种风格方案
- 两种镜头节奏方案

#### 确认卡消息

例如：

- 改全局风格会影响 12 个镜头，预计消耗 80 credits，是否继续

#### 系统反馈消息

例如：

- “Shot 8 已重新生成并替换到时间线。”

### 7.3 右侧聊天输入框

支持：

- 文本输入
- 发送
- 引用当前选中对象

第一版可选支持：

- 拖图进入聊天

## 8. 选项卡与确认卡设计

### 8.1 选项卡

必须支持结构化渲染，而不是只显示 JSON。

每张卡片可展示：

- 标题
- 简短说明
- 成本差异
- 适用场景
- 选择按钮

### 8.2 确认卡

确认卡至少展示：

- 本次动作是什么
- 会影响哪些阶段
- 预计消耗
- 是否可回退

按钮：

- 确认
- 取消
- 稍后处理

### 8.3 决策持久化

用户点击后：

- 前端更新本地状态
- 提交到 `pending_decisions`
- Project SSE 返回状态确认

## 9. 前端状态管理设计

### 9.1 状态来源分层

前端状态建议分成四类：

#### A. 服务端事实状态

来源：

- REST API
- Project SSE

内容：

- 项目
- 当前阶段
- active versions
- shots
- storyboard
- clips
- timeline

#### B. 会话状态

来源：

- Chat API
- 用户当前交互

内容：

- 当前输入框内容
- 当前选中的对象
- 当前待确认卡

#### C. UI 状态

内容：

- 哪个 tab 打开
- 哪个 shot 正在查看
- 哪个面板折叠

#### D. 本地缓存状态

内容：

- 上次查看的阶段
- 滚动位置
- 临时表单值

### 9.2 推荐实现

建议：

- 服务端事实状态：`React Query / TanStack Query`
- 轻量 UI 状态：`Zustand`

原因：

- 查询缓存和 SSE 协作容易
- UI 状态不必塞进复杂全局 store

## 10. SSE 驱动设计

### 10.1 前端维持两条流

和前面 API 文档一致，前端要同时维护：

#### A. Chat SSE

来源：

- `/v1/chat/completions`

负责：

- Assistant 文本增量
- tool call 信息

#### B. Project SSE

来源：

- `/api/v1/projects/{project_id}/events/stream`

负责：

- Pipeline 节点状态变化
- shot 更新
- timeline 更新
- decision 请求

### 10.2 为什么双流

因为：

- Chat 流关心的是“对话”
- Project 流关心的是“业务状态变化”

这两者混在一起会导致前端很难处理。

### 10.3 SSE 更新后的前端策略

收到项目事件后：

- 局部更新缓存
- 必要时触发重新拉取某一块数据
- 不全页刷新

例如：

- `shot.updated`：只刷新 shot 列表和当前 shot 详情
- `timeline.updated`：只刷新 timeline 视图
- `project.stage.changed`：更新左侧 Pipeline

## 17. 当前阶段后的开发思考

这部分先不写详细排期，只先明确“开发顺序要受前置结果约束”。

### 17.1 开发顺序本质上就是流水线

你的理解是对的，这个系统的开发顺序天然也是流水线式的。

因为：

- 没有项目和状态，就没法做工作台
- 没有 API 和 SSE 协议，前端只能空转
- 没有 shot / storyboard / clip 数据结构，工作区组件无法稳定开发
- 没有版本和追溯信息，前端回退与调试无从设计

### 17.2 所以前端开发顺序应该建立在后端前置结果上

前端真正合理的顺序应该是：

1. 登录页与项目列表
2. 项目工作台骨架
3. 左侧 Pipeline + 顶部项目状态
4. 右侧 Chat 与 SSE
5. 输入、音频分析、brief、shot plan 这些纯结构页面
6. storyboard / clips / timeline 这些媒体页面
7. 版本与回退 UI
8. 决策卡与确认卡完善

这说明：

- 前端不是先画大而全原型
- 而是要跟随后端稳定结果逐步展开

## 18. 你补充的工程原则，当前先记为后续执行计划前置约束

下面这些约束非常重要，虽然这份文档不展开实现细节，但必须作为后续开发计划前置规则：

### 18.1 阶段产物全部可追溯

- 参数配置从配置文件读取

### 18.3 提示词全部外部化

要求：

- 不允许把系统 prompt、任务 prompt、编译模板硬编码在业务代码中
- 必须放在外部模板文件中
- 便于热修、调优、迭代

## 19. 当前结论

现在前端初步设计可以先拍板这些结论：

- 主工作台采用三栏结构
- 左侧是 Pipeline，中间是阶段产物，右侧是 Chat
- 前端维护双 SSE：Chat SSE + Project SSE
- 前端状态按“服务端事实 / 会话状态 / UI 状态 / 本地缓存”分层
- 工作区按阶段切换视图，不做统一大杂烩
- 第一版时间线做轻量，不做重编辑器
- 版本、确认、选项、局部返工都必须是显式 UI
